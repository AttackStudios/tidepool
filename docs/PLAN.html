The constraint that shapes everything

Verified — this inverts the obvious plan

Both major mod platforms refuse to create a game page in advance. Thunderstore requires "pre-existing mod developer interest" and mods "ready for immediate upload," requested by hand in their Discord #game-requests channel. Nexus Mods only approves a new game entry when you already have ready mods attached to the request.

So there is no spot to reserve. Whoever shows up first with a working mod in hand founds the community and becomes its default. That makes day 1 a race decided by how fast a working artifact exists — and it means the 17 days before release should be spent building everything that doesn't need the binary, so that on Aug 25 you are only filling in the game-specific gaps.

Everything that doesn't need the binary

Roughly 80% of a mod manager is game-agnostic: profiles, install/uninstall, a package index client, and launching the game with the right injector arguments. None of that needs Surf Sandbox to exist.

  • NamePick and claim the brand across GitHub org, Discord, and a Thunderstore team name. One name everywhere.
  • RepoPublic GitHub repo with README, license, CI that builds and attaches release artifacts on tag.
  • ManagerBuild the manager shell: mod folder layout, per-mod manifest, dependency resolution, profile switching, one-click launch with Doorstop args.
  • IndexThunderstore API client — package listing, version resolution, download and unpack. Works against any community, so it's testable today against an existing game.
  • TemplateA BepInEx plugin template project that compiles, so day 1 is edit-and-build rather than scaffold-from-scratch.
  • CopyDraft the Steam guide, the GameBanana page, the Thunderstore request post, and the README — written and waiting, so publishing is a paste.
  • ContactMessage nocanwin. Ask whether mod hooks or an official API are planned. A yes could delete the entire reverse-engineering phase.

Triage, patch, publish

The whole day hinges on one question answered in the first five minutes, so it comes first.

If you find

Assembly-CSharp.dll

MONO — writing patches same day

In SurfSandbox_Data/Managed/. Decompiles to readable C# in dnSpy or ILSpy with real method and field names. Drop in BepInEx and you're patching within the hour.

If you find

GameAssembly.dll

IL2CPP — add ~1 day of scaffolding

Alongside il2cpp_data/. AOT-compiled to native; needs Il2CppDumper or Cpp2IL to recover metadata, then BepInEx 6 with Il2CppInterop. Still very much doable.

H+0:00
Install and triage

Buy, install, verify files. Check the Managed folder to settle Mono vs IL2CPP. Note the Unity version from globalgamemanagers. Confirm whether Steamworks assemblies are present — that decides the multiplayer transport later.

H+0:30
Loader in

Install BepInEx for the matching backend and architecture. Confirm it injects and writes a log. This alone is the artifact half the community will need first.

H+1:00
Decompile and map

Find the two classes that matter: the wave/water simulation and how its state is stored, and the surfer controller. Everything downstream — mods and multiplayer both — is decided by what those look like.

H+3:00
Proof-of-life mod

Smallest real Harmony patch that visibly changes the game — a debug HUD reading wave height and surfer velocity. It proves the toolchain end to end and doubles as the reference example for other modders.

H+5:00
Ship v0.1.0

Tag the release. GitHub release with the manager binary, the loader pack, and the example mod. This is the moment you are objectively first.

H+5:30
Plant every flag

Publish to the ungated platforms immediately, then file the gated requests with the working mod attached. Order matters — see the distribution table below.

H+8:00
Be present

Post the Steam guide, answer every question in the discussions and the Discord. Day-1 goodwill is what makes yours the default manager instead of a footnote.

Multiplayer

The genuinely hard piece, made tractable by this game specifically. A 2.5D surf sim with editable ocean-bottom contours almost certainly stores its wave as a heightfield array over a bathymetry profile — hundreds of floats, not a 3D FFT ocean or a particle fluid.

That means you can broadcast the entire water state from the host at ~20Hz and skip cross-machine float determinism altogether — no lockstep, no rollback. Host runs the only real sim; clients render it and simulate their own surfer locally, sending transforms up. Transport over Steam P2P lobbies if Steamworks is present, giving NAT traversal and friend invites with no port forwarding.

  • 1Confirm the water state shape and size in the decompiled sim. This validates or kills the whole approach — do it first.
  • 2Two-client transform sync with interpolation. Ghost surfers in a shared lineup.
  • 3Host-authoritative water broadcast plus level hash check so everyone rides the same break.
  • 4Lobby UI, invites, and manager integration that auto-syncs the host's mod set.

Running it on an Apple Silicon Mac

Surf Sandbox ships Windows-only — the Steam page lists no macOS or Linux build, just Windows 10 64-bit and DirectX 11. On an M1 there is no Boot Camp. This is the single biggest logistical constraint on the plan, and it splits the work cleanly in two.

The split that makes this workable

Everything you build runs natively on the Mac. The .NET SDK is native on arm64, and a compiled mod is just a DLL — platform-independent. Decompiling is native too: Rider ships an Apple Silicon build with a built-in decompiler, and ilspycmd installs as a dotnet global tool. Il2CppDumper and Cpp2IL are .NET and cross-platform. dnSpy is the only Windows-only tool in the chain, and you don't need it.

Only running and testing the game needs Windows. That's the gap to fill — and it's smaller than it first looks, because day-1 triage is all file reading, not gameplay.

You can start before you have Windows at all

Steam on macOS won't install a Windows-only title, but SteamCMD will happily pull the Windows depot onto the Mac if you force the platform type:

steamcmd +@sSteamCmdForcePlatformType windows +login <user> +app_update 4480760 validate +quit

That puts the real game files on disk natively. The Mono-vs-IL2CPP check, the decompile, and mapping the water sim and surfer controller are all just reading those files — so the first three hours of launch day can happen on the Mac at full speed, with no compatibility layer involved. Windows is only needed once there's a patch to actually run.

Four ways to get a Windows environment

Best for the full roadmap

A cheap Windows PC

~$150–300 used mini PC

Sounds like overkill until you remember the roadmap ends in multiplayer — which needs two game instances on two machines to test at all. A second box isn't overhead here, it's a requirement you were always going to hit. It also gives you a true target environment for the manager.

Best single purchase

Parallels Desktop

Windows 11 ARM VM

The game asks for 4 GB RAM, a GTX 1050 and 1 GB of disk — trivially within what Parallels handles. You get real Windows, so you can test the manager's installer, path handling and launch arguments exactly as your users will experience them. Wine will quietly lie to you about all three.

Cheapest that works

CrossOver

~$74 · Whisky is dead

Whisky was discontinued in April 2025 and its own developer pointed users at CrossOver. CrossOver 26 handles far heavier games than this one. Fine for the decompile-and-patch loop; weaker as a place to validate a Windows distributable.

Free option

Sikarugir

Free · formerly Kegworks

Renamed and modernised in October 2025, with D3DMetal, DXVK and DXMT backend toggles. Worth trying first precisely because it costs nothing — if the game runs, you've saved the CrossOver licence.

The one gotcha under Wine or CrossOver

BepInEx will silently fail to start under any Wine-based layer unless you tell it to. BepInEx works by having the game load a local winhttp.dll from its own folder, and Wine prefers its system DLL instead. The fix is a DLL override — WINEDLLOVERRIDES="winhttp.dll=n,b" in the launch options, or adding winhttp under the Libraries tab in winecfg. BepInEx documents this officially, so it's a supported path rather than a hack. Note that there are open reports of friction with the newest Wine and Proton builds, so budget an hour for this and don't discover it at hour zero on launch day. A VM sidesteps the issue entirely.

What could go wrong

High
Early-development churn breaks patches

The store page says features may change. Patches matching on IL offsets or field ordering will break with every update. Match on method signatures, pin a known-good game version, and version-gate the loader so a mismatch fails loudly instead of corrupting a save.

Medium
Water isn't a simple heightfield

If the sim turns out to be particle-based, host-authoritative broadcast gets expensive and the multiplayer plan needs rework. This is why mapping the water class is step one of both day 1 and the multiplayer phase — it's cheap to check and it invalidates a lot if wrong.

Medium
Gated platforms stall

Thunderstore and Nexus approvals are human-paced and may take days regardless of how ready you are. Mitigated by the ordering above: GitHub, Steam and GameBanana establish you publicly while the requests sit in a queue.

Medium
Mac-only dev setup slows the day-1 loop

The game is Windows-only and you're on an M1. Decompiling and building are native and fast, but every test run crosses a compatibility layer or a VM. Sort the Windows environment out during the prep phase, not on launch morning.

Low
Legal or EULA restrictions

No DRM, no anti-cheat, and a ships-with-level-editor design all point to a mod-friendly stance. Still read the EULA on release day before publishing anything.

Low
Someone else gets there first

It's a small pixel-art indie surf sim, not a viral phenomenon — the field is likely empty. The prep phase is what makes this near-certain rather than merely likely.

The one thing I can't do

I can't buy the game or log into Steam — that needs your account. Once the files are on disk (via SteamCMD with the forced Windows platform type, or a Windows install), the triage, decompile, patching and publishing are all things I can drive natively on the Mac.

Between now and then, none of the prep work is blocked. The manager, the repo, the plugin template and the draft copy can all be built starting today.
